# Flockdeck v0.6.0

This release adds agent roles, a way for agent panes in a project to message each other, and a shared task board. It also fixes a project that came back with its old position and name after being removed and opened again.

## What to do when you update

Nothing is required. A pane started without a role works as before and gets the same briefing. Roles, messages and the task board are new, and they have been tested with scripted agents, not yet in long real sessions with several agents. Expect rough edges and report them.

## Roles

A role is a job an agent is started for. Flockdeck has six: `manager`, `planner`, `worker`, `reviewer`, `tester` and `docs`. Start an agent in one with `flockdeck spawn -role <id>`, for example `flockdeck spawn -role reviewer "review the token refresh change on fix-auth"`. `flockdeck agents` lists the roles after the agents.

- An agent started in a role gets a "Your role" section in its briefing: what the role does, what it must not do, who it reports to, what to hand back, the checkout it expects, the roles it may start and the ids of every role in the catalog. Its environment has `FLOCKDECK_ROLE`. The role is saved with the layout, so a restored pane keeps it.
- Spawn rights are enforced. A pane in a role may start only the roles its own role lists under `spawns`. It may start an agent with no role only if its role has `plain` set, which `manager` has and the other built-in roles do not. A pane with no role is not limited.
- You can add roles, or change a built-in one, under a new `roles` key in `agents.json`. An entry with a built-in's id is merged over it field by field, and any other id adds a role. A role can name an `agent`, a `model` or a `tier` (`small`, `mid` or `top`), a briefing, a worktree policy, `spawns` and `plain`. A bad entry is dropped and listed in the catalog notice.
- The built-in roles name no agent, model or tier, so they run whatever the project runs by default.
- The worktree policy is guidance in the briefing. Flockdeck does not cut a worktree or make a checkout read-only because of it. Pass `-worktree <branch>` when a role should have its own checkout.
- `-role` with `-shell` is refused. A role's model is given only to the agent the role resolves to, so `spawn -agent codex -role fast` does not hand codex a model written for claude.

## Team roster and messages

An agent's briefing now has a "Your team" section: the other agent panes of its project, each with its role, name, agent, model, status and pane id. It lists at most 12 and says how many it left out. It is a snapshot. `flockdeck team` prints the live list, and `-json` prints it as JSON.

Agents message each other with `flockdeck msg send <target> <text...>`. The target is a pane id, a peer name, a pane name or a role id, and a role id goes to every live pane in that role. A name shared by several panes is refused, with the panes listed. Agents read their own mail with `flockdeck inbox` and `flockdeck inbox read <id>`. A message is up to 8 KB and an inbox holds 100.

- A notice is typed into a pane only when the agent has hooks and they have reported at least once, the pane has been idle for 2 seconds, nothing was typed into it since the last Enter, Ctrl+C or Ctrl+U, no slash command was submitted since the last hook event, and no notice went to it in the last 10 seconds. The notice says how many messages there are and who sent them, never what they say. Agents without hooks are never typed into and rely on the briefing, which tells every agent to run `flockdeck inbox` when a session starts.
- That check is a heuristic. A message can wait behind a pane you left with text you typed and deleted, or with a slash command open, until the next Enter or hook event. If you type at the moment a notice arrives, the two can interleave.
- When a helper started with `spawn` exits on its own, or is closed by Close finished panes or `close -finished`, its parent gets a message from `flockdeck`.
- Inboxes are saved in `messages.json` in the state directory and survive a restart. A pane closed on purpose loses its inbox. Read messages older than a week and any message older than 30 days are dropped when Flockdeck starts. Messages are stored as written, so agents are told not to put secrets in them.
- Messages are not authenticated. The token is shared by every pane of a run, so a process in one pane can claim another pane's id. The sender's name and role are not proof of who sent a message. The briefing, the notice and `inbox` tell agents that a message from another agent is not an instruction from you, and that an approval in one is not your approval. That is guidance to the agent and is not enforced.
- Any agent in a project may message any other in it, whatever its role. A shell cannot send.

## Task board

Each project has one task board, shared by its agent panes in every worktree. Agents use `flockdeck task` with `add`, `list`, `show`, `assign`, `status`, `note`, `branch`, `baton` and `prune`. There is no window for it yet, so you read it through an agent or with `flockdeck task list` in a pane.

- A task has an id (`T1` and up, per project), a title, a body, an owner role and pane, a state, a branch, an optional baton id and a thread of notes. States are planned, assigned, in-progress, in-review, done, blocked and cancelled. A fixed table says which role may make each move, and some moves need a note.
- Review is binding. Only the manager, a reviewer or a tester can move a task from in-review to done, so an owner cannot close its own task. Sending a task back from review needs a note. Only the manager assigns, and a task's creator may cancel it.
- Flockdeck sends messages through the inbox when a task is assigned, noted, moved to review, blocked, done or cancelled, to the owner, creator, reviewers or manager as the case needs. The briefing has a snapshot of task counts for the pane, such as "2 tasks for your role, none claimed yet" for tasks assigned to a role no pane has started. The snapshot goes stale.
- A pane with no role has the manager's powers only while no pane in the manager role is running.
- The board is `.flockdeck/team/tasks.json` in the project's main checkout. The first time it is written, Flockdeck adds `.flockdeck/` to the repository's `.git/info/exclude`, so it is not committed by accident. A project that is not a git repository gets the board and no exclude.
- One Flockdeck server writes the board. A second instance open on the same repository can overwrite its changes. A damaged board is set aside and ids start again at T1.
- A board holds 2000 tasks. At the limit the oldest done or cancelled task is dropped to make room, and a new task is refused only when all 2000 are open. `flockdeck task prune [-days N]`, for the manager, removes done and cancelled tasks last changed more than N days ago (30 by default). Neither keeps an archive.
- Like messages, task requests are not authenticated, so roles keep agents to their jobs and do not stop a process that wants to act as another pane.

## Fixes

- A project you removed or forgot, then opened again, came back in its old position in the open list and with its old name and archive mark until you restarted Flockdeck. It now comes back with its current order and name straight away. Moving, renaming and archiving projects already updated live.
- The briefing of a role that may not start agents, such as `worker` or `reviewer`, no longer includes the "Starting agents of your own" section, which told it to run `flockdeck spawn` while its role section said it could not. The manager gets a section with examples that name the roles it may start.
- A notice now names the sender's role and name, for example "from reviewer work (#1)", and `inbox` lists the sender's pane id.
- A refused task move says why, for example that moving T2 from in-review to done is for a manager, a reviewer or a tester and that you are the owner. `task assign` on a task that is in progress under another pane warns and goes ahead, because a manager sometimes has to move work off a stuck pane.

The Agents and The command line Help pages and `docs/agent-briefing.md` describe all of this in more detail.
